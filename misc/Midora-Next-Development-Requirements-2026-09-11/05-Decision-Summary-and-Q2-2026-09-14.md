## 1. 检查结论与阅读方法

- Q1 的 **95 项全部有回答** ，没有漏答；“同意”按用户统一说明解释为同意该项 Q1 推荐，明确修订优先。已回答不等于所有原推荐获批：Lane 显隐继续讨论，导入 PC 包装分支已撤回。
- 原稿前 32 个一级需求均有 R01～R32 对应项，没有发现整项遗漏；优先级仍为 P0 7 项、P1 7 项、P2 9 项、P3 8 项、P4 1 项。用户草稿其后的历史条目不自动并入本批。
- 新增 **9 项 Q2 边界问题** ，其中 1 项动效问题仅属发布稳定后的后置阶段。它们不是漏答，不需要重答原问卷，也不包含新的图标选择题。
- 原问题、原推荐、用户原话都保留在 [04](04-Decisions-and-Preparation.md)。以下是归纳，不是用户原话替代品；详细回答仍只填写04，避免出现两份不同答案。
- 已确认的新需求尚未改入 SRS／ADR／实现；规格变更应在对应实施切片正式落实。问答中的模型、声音、持久化和并发决定不应由代码默认值代替。
- Win10 环境已回答为“可提供虚拟机、无实机”；它不是缺答项，也不是已完成的兼容性测试。

## 3. 对回答中技术疑问的答复

### 3.1 Lane 目录和精确计数，不必每次打开都 O(N)

**源码确认：** 当前 `PresentationModels.ScheduleMidiTargetDiscovery` 存在 `QueryValues(0, long.MaxValue)` 全范围发现路径；`TimelineEventTargetIndex` 也有全源按 target 分组／建数组。现有实现不能直接被描述成已具备廉价的全 target 计数。

**可行方案（尚未实现／计时）：** 在导入／分页构建已经遍历数据时顺带建立 owner＋target 的摘要；编辑按命令最终结果维护 old／new 计数，碰撞覆盖、删除、Undo／Redo 都走同一正式事务。目录读取摘要，成本随 target 数 K 而非事件总数 N 增长，虚拟化展示。只有曲线或 Mapping owner、没有点的 target 也可显式标明来源，不强行编造点数。

旧项目首次缺摘要仍可能需要一次 O(N) 后台构建；期间显示“统计中”，可取消、不阻塞 UI、不把未知写成 0。普通刷新／打开目录不重复全量扫描，摘要不能常驻第二份完整事件对象数组。哪些 Tab 可隐藏及用什么入口查回仍是用户工作流，见 D-LANE01.g；这不需要为了性能迫使用户保留所有 Tab。

### 3.2 琴键染色不能以读图像的一列替代音符时间语义

用户提出“读取播放位置 1px 的图像”可作为显示实验，但不能直接证明 Gate 正确：

- 水平缩小时一个像素可能覆盖多个 Tick；极短音符又会至少画成 1px，图像占据不等于 `[start,end)` 仍活动。
- 边框、抗锯齿、透明度、选择／预览和 Onion 层叠都会改变该像素；只扣除边框不能消除其他差异。
- 冷瓦片未就绪或旧内容正在替换时，音乐数据与当前图像可能暂时不同；不能据此让应该亮的键消失。
- MIDI Key 为 0～127，共 **128 个** 。即使只查每个 Key 一点，图像同步／读回成本也不能仅用“查128个点”估计。

建议使用正式范围索引派生每 Key 的有界占用／来源色摘要或增量端点游标，只查当前 Tick 附近，不扫描整工程；不从 bitmap 反推命中或音乐事实。该思路与 SRS §18.11.2／§18.11.3 及现有只读投影边界相容，具体成本要用冷／热页和多来源实测。维持已确认的 Gate、当前轨道颜色优先、最上层来源、不按 Mute／Solo 过滤；性能不合格则暂缓，不改成未批准的近似语义。

### 3.3 同目录文件并不消除剪贴板协议、生命周期和文件冲突

**源码确认：** 当前 `ProjectObjectClipboard` 仍依赖进程内 Session Identity／引用身份；主窗口向系统剪贴板写的是文本摘要，正式对象留在私有 clipboard；底层 storage lease 也不等于跨重启可发现的持久索引。

同 ProgramRoot 文件型方案可以避免大内容全驻内存，符合用户的空间位置要求，但仍需独立的完整性／长度校验、原子发布、有限内存、接收 lease、崩溃回收和磁盘不足处理。重新打开目录不代表某个半写文件就可安全粘贴。不同目录配置／剪贴板隔离也不意味着可以忽略两个安装位置同时打开同一项目文件的写入冲突；文件身份及已有可写会话保护必须按项目文件本身落实，不以安装目录代替文件身份。

跨重启继续粘贴已确认；是否采用单个持久当前槽、它与外部系统文本剪贴板的关系，以及同目录原地升级后的策略，见 D-MI06.a/b，这些具体边界仍待答。无需重新决定已确定的 Note／复杂依赖范围、TPQN、跨实例独立 Undo 等。

### 3.4 需要澄清的是“另一类契约”，不是要求重答

- **显示值与 Mapping：** Q1 的具体问题举 Batch Edit，原推荐同时提过 Mapping；用户回答“表达式也改”足以确认工具表达式，但不足以判定整条 Project Mapping 音乐链也改。原 R12“底层值不变”本身也不能证明 Mapping 必须 raw——它同样可以显示域计算后编码回 raw。因此工具显示域／Mapping 保留原语义只是 Q2 推荐，不伪装成用户已批准的限制。见 D-VAL01.d。
- **删除 owner 与引用 owner：** 删除 B 后 B 的 Tab/profile/缓存必须释放，和存活 A 是否保留指向 B 的一个失效 Onion ID 并非同一个资源。SRS §18.11.3／INV-116 当前有 dormant 来源与 Undo 恢复语义，故将这个区别明说，见 D-STATE03.d，不保留重型资源来钻需求空子。
- **手动 pan 后恢复跟随：** 源码 `MainWindow.xaml.cs` 的现有中键／概览平移在结束或失去捕获后恢复；D-VIS02.d 已要求保留原行为，不再把恢复时机作为新问题。只有全局连续状态在其他视图的衔接需要 D-VIS02.f。
