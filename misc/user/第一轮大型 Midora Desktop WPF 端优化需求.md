# 第一轮大型 Midora Desktop WPF 端优化需求

## 概述

本文档是在用户在 2026/8/9 21:15 （UTC+8）试用本软件过程中，发现到的BUG和优化需求。

试用功能范围其实非常窄，基本上没动大部分高级功能，但确实仍然发现了许多值得马上修复的问题。

该版本试用总体感受是，底层功能大部分是可用的，能看出来大部分行为和边界的处理是正确的。

问题集中在一些确定性的BUG、功能缺失/需改进、交互体验、综合用户体验等方面。

下面列出的是第一轮问题，后续预计还有很多轮。

## BUG

### SubVoice 的底部键盘 Held Preview 无论鼠标按下多久，其持续时间均很短

在底部键盘上按下，预期行为是直到鼠标松开为止都持续，但现在的行为是无论按下多久，只持续短暂的时间，且会在松开前就 Stop。

在钢琴卷帘的左侧按下，其行为却是预期的，直到鼠标松开为止都持续。

### 新项目，SoundFont 在指定后尝试播放/预览，会始终错误地提示“A verified Project SoundFont is required.”

用户必须保存Project，然后重新打开Project，才会正常。

此外，在项目设置中，无论是否已重新打开项目，无论是否可真正地发声，音色库设置那边似乎始终提示“No SoundFont is a legal Project state. It disables ...”这行字。这明显是不对的。

### 在 SubVoice 的钢琴卷帘左侧琴键区预览音符时的 BUG

当用户在 SubVoice 未插入音符时，预览都正常。

插入了一个音符时，在 SubVoice 琴键左侧预览，会错误地将该音符视为在逻辑轨道上按下的音符，并在此基础上错误地判定 MIDORA2101 （音符键超出范围）。

SubVoice 上钢琴卷帘琴键左侧预览音符时，应该始终视为“在这个SubVoice上”的音符预览，而不是错误地视为在外层触发这个事件乐器，这里的预览只是听听音高罢了。在事件乐器上的底部琴键预览时，则不同，它应该确实是视为在外层触发事件乐器的逻辑Note。

### 在绘制逻辑参数曲线时，若为整数类型，始终触发“必须为整数”错误

整数值的绘制曲线/点应该自动与鼠标位置取近似值，不然没办法画。

### 事件 / 参数视图与上方的钢琴卷帘视图完全没对齐

这是因为它们左侧的内容宽度不一致，一个是琴键，一个是事件/参数列。先结合本文后面的需求，确定布局后，想办法将其对齐。

## 功能

### 现在的 Grid 功能和 Snap 功能不符合需求

现在的编曲手感非常差，大部分是因为现有的 Grid 功能和 Snap 功能并不好用。

可能要大幅改 SRS 和对应代码。

用户真正想要的是：

- 逻辑轨道和钢琴卷帘上的设置相互独立，而不是共用；

- 粒度单位不应该是“四分音符”，而是“四个四分音符”，即：1/1代表四个四分音符，1/2代表2分音符的粒度，而不是8分音符，1/8代表8分音符的粒度，而不是32分音符，这样设计更加直观。

- 粒度的预置应有（要显示名称，例如四分、三连8分、附点16分等）：小节（这取决于拍号事件状态，需要特殊处理）、1/1、1/2、1/3（三连2分）、1/4、1/6（三连4分）、3/16（附点8分）、1/8、1/12（三连8分）、3/12（附点16分）、1/16、1/24（三连16分）、3/64（附点32分）、1/32、1/48（三连32分）、1/64、1/128、1/256。

- 提供“分割线粒度”（都默认4分音符）和“操作粒度”（都默认16分音符）两种独立的设置，显示的粒度和实际操作粒度应允许不一致；

- 为了简单，粒度设置和 Snap 启用与否仍不保存进项目文件，且跨 Segment 的钢琴卷帘上共用一个设置，但轨道视图的设置要与钢琴卷帘的独立；

- 用户可以自定义粒度值，可以指定任何整数值分之 1；

- 当 TPQ 乘以 4 乘以粒度时，可能会出现小数Tick，所以直接对粒度的实际 Tick 值取 Ceiling，这样保证最小输入 1 Tick并取近似；

- 仍然提供“Snap”开关，应用的是“操作粒度”，Snap未启用时，实际上操作粒度仍然存在，即 1 Tick；

- Snap 启用时，“操作粒度” 影响：选择框开始时间和时间长度的粒度、时间范围选择的开始和时长的粒度、编辑光标定位粒度、播放光标定位粒度、Segment / 音符的放置位置粒度、Segment / 音符的长度调整量粒度（注意：不是应用到总长度，不要把总长度自动吸附到粒度位置上，而是应用到长度“调整量”）、选择的 Segment / 音符的拖动位移粒度（注意：不是应用到最终位置，不要把位置自动吸附到粒度位置上，而是“位移量”的粒度）

### 用户无法预先指定 Segment / 音符的创建时长度，音符无法预先指定力度

对应视图右上角，在粒度设置旁边需要有个输入框，输入即生效的输入框，指定创建 Segment 的长度、指定创建音符的长度和力度。

默认长度现在直接是粒度的值，这是不好的行为融合，粒度和默认长度不应该绑定在一起。

长度以 Tick 为单位即可。

并且，在钢琴卷帘，Draw 模式下点击一个音符时，应自动将默认长度调整为该音符的长度 Tick。

粒度设置改变时，默认长度不应跟着改变，且默认长度应允许小于粒度，粒度设置不应干涉创建时的长度。

### Draw模式下，Segment / 音符 在鼠标的位置没有放置位置和长度的预览

现在用户只能靠鼠标位置目测，这体验不好。鼠标的位置应该有个位置+长度的视觉预览，以确切地告诉用户如果在这里新建后会是什么样子。

视觉预览应为虚线边框，与实际存在的 Segment / 音符作区分。

在轨道视图下，如果鼠标位置下 Segment 位置和长度会导致overlap，则把预览图形标红，代表将拒绝在这个位置创建这个长度的 Segment。

### SubVoice 的钢琴卷帘，用户无法指定粒度，无法开关 Snap、无法指定默认长度和力度

SubVoice 内也应该有这个功能，同上面的需求。

### 现在貌似没有音符力度视图

无论是 Segment 还是 SubVoice 都需要音符力度视图。

就放在事件编辑 / 逻辑参数编辑视图里，可切换音符力度编辑 / 参数（事件）编辑两种模式。

音符力度以柱状展示，这里不关心音符的具体key，只关心把所有音符在x时间轴上排列，然后每个音符变成一个柱子，柱子高度代表力度。并且鼠标点击 / 拖动时直接编辑力度，不能在这里拖动音符位置。左键+拖动时自由编辑，拖动途中遇到柱子则直接编辑力度到鼠标对应的y -> 力度值；右键+拖动时则画一条直线，例如在x=0tick下在y=24力度点击鼠标右键，开始拖动，拖动到x=192 y=100力度，那么就视为x=0~192范围内的所有音符的力度值以这两个点决定的直线的对应x值求得y值。一次拖动算一次动作，因此undo/redo时以一次拖动为单位。

### 现在每个事件 / 参数编辑都是垂直放置的，而用户需要让某一个特定事件 / 参数单独展示

曲线是很需要微调的东西，现有的非常矮的多条曲线垂直放置展示根本不能用。

因此很需要用Tab或其他方式分页展示，然后一整个单独展示某一个事件/参数的曲线/点。

单独展示时，应在左侧显示基准值，并允许垂直方向（独立于钢琴卷帘）缩放。

单独展示时，要显示基准值和基准线。例如只允许0-127的参数来说，在缩放最小时，就展示0 - 32 - 64 - 96 - 127 这样，然后给这些值的位置给右侧画浅的横基准线。

放大后显示更细的基准值，缩小后显示更粗的基准值。

不需要保留原先的垂直放置所有事件/参数的显示方式，太难用了。

列表（或Tab）+单独显示一个选定的事件/参数才是正确的设计。

## 交互

### 空格应始终为“播放/停止”键，除了文本输入、有弹窗等情况之外

现在的空格有时会错误地指向某个按钮的按下操作，用户不应该关注焦点是否在正确的地方，绝大部分时候用户按下空格就是想要播放/停止操作，而不是按下某个莫名其妙的按钮。

### Segment / 音符的 HitBox 过大

鼠标明明不在Segment / 音符的边界内，点击时仍然能点到。这导致了如果想在相邻处放置 Segment / 音符时，操作非常别扭，很容易误点到前一个。

### 在钢琴卷帘的左侧琴键处 Ctrl + 鼠标滚轮，应该能够缩放垂直方向

现在只能缩放水平方向，用户想要让垂直方向也能够缩放。

## 用户体验

### 顶部提示栏和错误弹窗过于频繁

这个提示栏其实是很好的功能，本身应该保留。

但是它的出现条件应调整。现在但凡有点动作，都会有这么一行突然在顶部出现，用户体验不佳。

它应该在真正需要用户关注的致命问题出现时才出现。现在是连复制粘贴都要出现一下，出点小问题都要出现一下，用户觉得很烦人。

成功的操作和普通信息就不要顶部弹字了。

那么这些小动作和小问题，其实应该在整个程序最底部的那行状态栏显示。可以放在最右边，且非错误类用灰色，错误类用红色。

### 在逻辑轨道视图，插入 Segment 时，想在两个 Segment 中间建一个新 Segment，而两个 Segment 间隙小于新 Segment 的长度时，始终无法插入

原因是：“Segments on the same Logical Track cannot overlap.”

这个边界条件是正确的，也确实符合我们的 SRS 边界需求，这个边界判断不需要丢弃。

但实际上，现在的版本，用户并不能在新建前指定 Segment 的长度，所以这种情况下必须找一个空隙大的地方，新建，然后调整长度，然后再拖进想要的地方。操作十分麻烦。

建议改成：用户尝试在某个间隙小的地方新建 Segment 而长度大于间隙时，自动将长度缩短到最大可容纳的长度。

这并不违反边界，且用户既然想在小空间插入，那么用户一定是接受这种静默缩短的行为的。

但是，拖动、伸缩已有 Segment 导致了 overlap 的情况又不同了，此时仍然应该明确拒绝，这与创建 Segment 是不同的，用户可能不希望已存在的 Segment 被静默截断。

### 拖拽选择的音符到任何范围外，始终都会弹报错窗口

这个边界处理是没问题的，但可以进一步优化。

这个问题出在，不应该要求用户在所有的时候都能精确地拖到范围内。

例如，想把音符拖到Tick 0处、Note 0处、Note 127处的时候，用户需要操作得非常精准。

而用户想要的是，故意拖到范围外，以“确认”自己将对象精准地放到了边界处。

这是易用性问题。我希望用户在拖动对象到范围外时，程序应直接对其进行Clamp，让选择范围的对象整体不超出范围即可，而不是每一次操作不精准就弹窗，体验不佳。

这一点包含音符和任何可拖动的对象。

### 在进行 Held Preview 时，用户操作得快，没来得及等 Stop，尝试再次进行另一个 Held Preview 时，始终弹窗“Realtime Preview is currently locked.”

这不是BUG，反而是十分正确的阻拦。但不应该弹窗，用户会嫌烦，只在最底部状态栏提醒即可。

#### 关于 Held Preview 性能

用户操作的地方是 SubVoice 的钢琴卷帘左侧琴键区，其实操作速度并不快，但 Held Preview 却很容易跟不上。

说明现在的预览延迟有点高了。其实 Held Preview 完全可以不用预渲染的方式，这个预览的精度要求没那么高，用户往往只是想听听看大体效果，但现在软件却走了一整套过于复杂的渲染用的最严谨的机制。Held Preview 可以单独是一套独立的机制：直接向独立的非 Decode 的 Stream 发送事件，直出音频，也不需要那么复杂的缓存机制。

本次不需要修复这个延迟优化问题，这属于后期的性能提升优化阶段该做的事，性能优化这一点本次只做记录即可。

但是，本次先把“放置音符时播放预览”的功能砍掉，不然现在每次放一个音符都要卡一下。
